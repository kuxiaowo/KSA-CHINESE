# Kitten Space Agency 汉化可行性评估

调查时间：2026 年 10 月 13 日，北京时间。对象为本机磁盘上的 **2026.10.13.5602**，不是对所有历史或未来版本的结论。

**结论：主要操作界面可以做较全面的汉化，适合采用“独立代码 Mod + 外置译文 + 中文字体”的组合。仅放入一个语言文件，目前不能完成主要界面汉化。只改显示层、不覆盖游戏文件，可降低对更新和存档的影响；游戏升级后仍需要兼容性复核。现阶段不能给出有证据支持的全游戏覆盖百分比，也不能承诺 100% 或永久兼容。**

**原生语言资源的实际边界**

`Content/Core/Languages.xml` 只登记 `Languages/en-US.resx`。该资源有 43 个条目：`Font`、`Language` 两个配置项，以及 41 条游戏文本，主要是提示和飞行计算机说明。

本机 `KSA.dll` 的核心 `KSA.LStrings` 类中，静态检查提取出 **213 个带明确 ID 的文本定义**：153 个 Settings、51 个 Alert、6 个 FlightComputer、3 个阴影过滤说明。因此随包 `.resx` 少了 **172 个已有代码定义**。把随包英文表当作完整翻译底稿，会漏掉大量已经接入原生文本系统的项目。

此数字表示该类的定义数量，不表示 213 个都已在可见界面出现，也不表示全游戏文本只有 213 条。调用位置仍需逐条审查。

更关键的是：本机语言类会加载并登记资源，但 `Languages.OnApplicationStart()` 为空；`Language._localisedStrings` 在检查到的代码中仅用于存储和统计，没有连接到译文提供器的读取路径。`Brutal.Localization.LStrings` 已提供 `SetLocalizedStringProvider`，游戏程序中未找到调用它来启用译文的路径。因此可以利用已有本地化框架，但仍需要少量代码把译文真正接入显示流程。不能仅凭“语言注册成功”认定屏幕已汉化。

源码还提供 `generatelanguage <locale>` 控制台命令，按当前已登记的 LString 导出模板。该命令会写入玩家目录，并在同名文件存在时删除旧文件，本次没有执行；之后宜在独立测试实例里使用。模板生成也不能导出仍未接入 LString 的文字。

根目录 `zh-Hans`、`zh-Hant` 中只有 `System.CommandLine.resources.dll`，是依赖组件的语言资源，不能作为游戏已有简繁中文的证据。

**可以翻译到什么程度**

| 内容 | 可行性判断 | 实现重点与边界 |
|---|---|---|
| 已接入 LString 的设置、警告、说明 | 较高，可先完成 | 通过文本 ID 提供译文；补全模板，保留占位符；部分定义仍须核对调用位置 |
| 主菜单、编辑器、轨道与转移规划、部件参数、快捷键名称 | 较高，但要逐个入口适配 | 仍有程序内字符串和动态拼接，需要针对显示调用做代码补丁 |
| 部件、推进剂、材料和天体显示名 | 较高，但语义审核量较大 | 显示时映射中文；部分名称来自 ID 或程序构造，不能只翻 XML |
| 仪表标题、按钮和悬停提示 | 当前版本已有可行入口 | 普通短标签现由 ImGui 绘制，必须同时适配仪表专用字体与显示路径 |
| 数字、单位、RCS、TWR、Δv、型号 | 按需要解释或保留 | 不必为追求覆盖率改动符号、计算格式和常用缩写 |
| 模型或贴图上的印字 | 需另行盘点 | 本次没有逐张查看纹理和模型；可能需要制作贴图补丁，维护成本更高 |
| 控制台命令、内部枚举、资源 ID、路径、存档键 | 保留技术标识 | 可以翻帮助说明，不改命令和实际数据键 |
| 版本历史、调试窗口、第三方 Mod | 可以另定范围 | 不纳入第一版主要操作界面的默认验收范围；第三方 Mod 需独立适配 |

静态候选清单还发现：Core XML 中有 27 处含英文的 `DisplayName`、108 处含英文的 `Label`、101 处含英文的 Tooltip `Value`，合计 **236 个候选出现位置**；分别有 26、82、96 个不同原文。这个统计按字段和英文字符筛选，未计入纯符号，也没有判定每一处是否实际显示。

另从含 `ImGui.`、`ImGuiHelper.`、`ConsoleWidgets.` 调用的代码行中提取到 **2,625 个字符串候选出现位置，2,111 个不同原文**。其中包含内部控件 ID、格式串和重复文字，同时会漏掉其他 API、跨行调用及动态内容。因此这些数字用于定位待核对项目，**不能作为全游戏文本总量，更不能直接计算汉化完成率**。

**中文字体与仪表的关键发现**

自带的 `JetBrainsMono-Regular.ttf`、`3270-Regular.ttf`、`MilSpec33558.ttf` 的 cmap 中，基本中日韩统一表意文字范围 `U+4E00–U+9FFF` 映射数都为 0，抽查的“中文轨道比冲”也都没有字形。汉化必须携带或注册合适的中文字体，并保证译文所需字符包含在字体中。

本机 `FontManager.Initialize()` 从安装目录相对路径 `Content` 递归搜集字体；Mod 的字体注册并不等于实际文件路径已经进入生成字体的列表。要把字体完全放在玩家 Mod 目录，还需要处理这条注册路径。普通 UI 字体由设置选择，仪表字体另固定查找 `MilSpec33558`；只更换普通 UI 字体不足以证明仪表也能显示中文。

当前 **5602** 的 `GaugeCanvas.DrawWidgetText()` 直接用标签原字符串调用 ImGui 文字绘制；`GaugeLabel.frag` 也说明字形已移至 ImGui，着色器仅绘制背景。因此早期社区资料所述“仪表文字只支持拉丁字母”的限制，不能原样套用到本机版本。旧的 6 位字符打包代码仍然存在，数字仪表仍使用字形图集，需按当前实际调用路径区分。静态证据支持继续研究中文标签，但未做图形运行验证。

建议为普通 UI 与仪表分别验证字体、缩放、截断、不同分辨率和 DPI；中文能显示并不等于按钮仍清晰可读。

**建议的交付格式**

面向玩家发布一个版本化 ZIP，包含独立 .NET 10 汉化插件、UTF-8 译文、中文字体及许可、安装与卸载说明、兼容版本信息。开发底稿采用带上下文的 JSONL；运行时原生文本可保留 `.resx`，扩展界面可采用结构化 JSON。两种格式都由同一份审核底稿生成，避免重复维护。

建议结构如下，仅是设计，尚未生成可安装包：

```text
KSAChinese/
  mod.toml
  KSAChinese.dll
  Languages.xml
  Languages/zh-CN.resx
  Locales/zh-CN.json
  Fonts/ChineseUI.ttf
  compatibility.json
  LICENSES/
  README-安装卸载.md
```

插件建议安装在玩家 `Documents/My Games/Kitten Space Agency/mods/KSAChinese/` 下，加载器放在独立工具目录，通过专用快捷方式启动。StarMap 作者明确推荐玩家 Mod 目录，说明该位置可跨游戏更新保留文件。[StarMap 加载器说明](https://github.com/StarMapLoader/StarMap)

`.resx` 是原生文本资源格式，JSON 是扩展显示词典，DLL 是接入与显示适配代码，ZIP 是发行容器。这几种格式承担不同职责，不是互相排斥的选项。翻译底稿中的键宜包含文本 ID 或模块、类型、方法与用途；不能只用英文原文做无上下文的全局替换。

需要保持原始控件 ID（包括 ImGui `##`/`###` 规则）、枚举值、资源模板 ID、存档键、型号、单位以及 `{Vehicle}` 等占位符。中文 UTF-8 字节数和字符数不同；遇到固定缓冲区或字符串拆分逻辑，必须核对长度与分隔符，不能只替换字面量。

发行包只包含汉化所需的自有或许可允许的内容。KSP 资源用于本机术语参考，不把其整套字典、字体或游戏资源塞进汉化包；KSA DLL 和反编译源码也不随包分发。

**对后续更新的影响**

| 方式 | 对游戏更新的影响 | 汉化自身维护 |
|---|---|---|
| 覆盖 `KSA.dll`、替换整套 Core XML | 游戏更新可覆盖补丁；旧补丁回装可能覆盖新功能或数据 | 最易绑定旧版本，不建议作为正常发行方案 |
| 只增加 `.resx` 的数据包 | 文件容易隔离，但当前缺少完整激活与显示接入，覆盖能力不足 | 文本 ID 越稳定，维护越轻；仍须检查注册与加载 |
| 独立代码 Mod + 外置词典 + 字体 | 可设计为不写游戏本体，让更新器处理原版文件；玩家目录中的文件保留 | 游戏方法、字段、加载器、原生绑定变化时仍需复核或适配 |

“更新后文件还在”和“更新后功能兼容”是两件事。采用独立 Mod 不会自动获得永久兼容性，也不等于运行中绝无干扰。正确设计应让未验证版本禁用不安全补丁，缺译文回退英文；加载失败应完整撤销已安装的本项目补丁，并能通过原版入口启动。

更新维护建议保存游戏版本、相关文件哈希、补丁目标签名、原始指令摘要、译文原文和审核状态。新版先比对文本 ID 与源文，再检查补丁匹配和安装，随后验证中文字体、控件行为及独立测试存档。不能通过简单放宽版本判断来宣称支持新版，也不应把语义发生变化的旧译文自动当作已审核译文。

只在显示时翻部件名称，并保留玩家自定义名称和持久化 ID，可显著降低存档风险；实际保存、载入、卸载回退仍必须测试后才能承诺。

**专业术语的核对方法**

本机官方 KSP 中文字典有 12,031 个匹配到的条目定义，Serenity 中文字典有 724 个；MechJeb 英文／中文文件分别有 1,188／1,183 个。MechJeb 的中英文件可以按同一 ID 对齐，官方字典则提供玩家熟悉的中文表达。条目数是行级定义统计，不代表不重复的术语数，也不代表本次已逐条阅读或审核。

已经看到同一术语存在译法差异：官方 KSP 使用“远点／近点”，MechJeb 使用“远拱点／近拱点”；MechJeb 部分条目把 eccentricity 译作“离心率”。因此参考 KSP 仍需核对具体物理量和当前界面用途，不能把任一已有译文直接当作唯一标准。

每个待译项应记录英文、中文草稿、界面及功能上下文、单位与参考系、KSP/MechJeb 对照 ID、语义备注、审核人或审核角色、源文版本、最终状态。对轨道、姿态、推进、热力学和材料术语分别做上下文审核：例如区分远点与远地点，区分 burn 的机动点火和燃烧反应，区分轨道法向与坐标轴，以及 pressure 所表示的腔压、动压或其他压力。型号、公式和化学符号单独保留。

实际翻译阶段可采用“初译 → 独立专业复核 → 一致性与占位符检查 → 游戏内检查”的流程；由我或获授权的多个智能体分别承担初译和复核，争议项再交回确认。源文变更后重新审核，而不是继续继承“已核对”状态。本次尚未进入逐条翻译与译文验收阶段。
